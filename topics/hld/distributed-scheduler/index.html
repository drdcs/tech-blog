Design a Distributed Job Scheduler

High-level architecture for a distributed job scheduler that runs and manages work at scale — lease-based dispatch, failure recovery without a global lock, and a control plane that shards before your metadata store becomes the bottleneck.

📋 1. Design details collection

A scheduler is not a cron with a database. At scale it is a dispatch plane — a system that accepts intent, durably records it, assigns work under capacity constraints, and recovers when nodes lie. The functional surface is deliberately small; the non-functional surface is where most designs live or die.

Functional

What the system must do

  • Submit & schedule jobs — accept job definitions (payload, queue, priority, retry policy, deadline) and place them into a durable queue with at-least-once delivery to workers.
  • Dispatch under constraints — match pending work to worker capacity (CPU, GPU, region, concurrency slots) without double-assigning the same run.
  • Track lifecycle — expose state transitions: pending → leased → running → succeeded | failed | cancelled, with idempotent status updates from workers.
  • Recover from failure — re-queue work when a lease expires or a worker stops heartbeating; apply backoff and dead-letter after max attempts.
Non-functional

What production will measure

  • Throughput: 10,000 API requests/sec peak; 4,000 job submits/sec sustained at peak.
  • Dispatch latency: p99 < 150 ms from enqueue (Redis) to lease grant under normal load.
  • Availability: 99.95% API via multi-region GSLB; regional failover < 60 s. Metadata RPO = 0 on Postgres commit.
  • Consistency: Redis holds the hot queue; Postgres is system of record. Lease CAS in Redis; async durability flush to DB.
  • Operability: per-tenant quotas, queue-level backpressure, Redis memory alerts per queue shard.
Scope boundary. This design covers batch + latency-tolerant async work (ETL, ML training steps, report generation). Sub-second cron with strict wall-clock alignment is a different problem — add a separate timing wheel or defer to the cloud vendor's scheduler.

🧮 2. Back-of-envelope discussion

Design target: 10,000 API requests/sec at peak. Split: 40% job submit, 35% status read, 25% worker callbacks (heartbeat + complete). Median run time 45 s, metadata 2 KB, 5% failure rate with 3 retries.

Orders of magnitude

The first bottleneck is usually Redis timer churn or broker partition throughput — not Postgres. Redis holds the near-term scheduling window; the message broker carries durable execution intent to workers. Cassandra absorbs high-volume run logs so Postgres never becomes a write-heavy event store. At 10× (100k req/s), shard Redis, add broker partitions, and scale scheduler nodes before upsizing Postgres.

Layer roles

What each hop does

  • GSLB — routes to the nearest healthy region; drains a region during failover.
  • L7 LB / gateway — terminates TLS, applies WAF and per-tenant rate limits.
  • Request router — sticky routing by queue_id or tenant_id for shard affinity.
  • Relay nodes — lightweight ingress path: validate payload, enforce quotas, hand off to scheduling pipeline.
  • Task management service — owns job/task configuration CRUD, status queries, cancel semantics.
Why split relay vs task mgmt

Service boundary

  • Relay scales on ingress QPS — mostly stateless, CPU-bound validation.
  • Task management scales on config complexity — richer queries, policy evaluation, audit.
  • Both are stateless pods; all durable state lives in the four storage layers below.

💾 4. Storage & queue layers

A production scheduler needs four distinct stores — each optimized for a different access pattern. Collapsing them into one database is how teams end up with a Postgres cluster that cannot keep up with log writes or a Redis instance pretending to be durable.

PostgreSQL

Relational DB — task / job config

  • System of record for job definitions, schedules, retry policy, and current run state.
  • Strong consistency on config writes; read replicas for status API.
  • Small rows (~2 KB metadata); not used for high-volume event logging.
Redis

In-memory — timer & scheduling buffer

  • Timers — sorted sets keyed by fire_at for delayed and cron-style jobs.
  • Buffer — near-term priority queue window (next N minutes of work).
  • Leases — short-lived claim keys while scheduler hands off to the broker.
  • Rebuilt from Postgres on cold start; not durable across full cluster loss.
Message broker

Durable execution queue

  • Scheduler nodes publish run_id + payload_ref when a job is ready to execute.
  • Partitioned by queue_id — workers in a consumer group pull with at-least-once delivery.
  • Decouples scheduling decisions from execution rate; absorbs worker slowdown without blocking Redis.
  • Dead-letter topic for poison messages after max retries.
Cassandra

Wide-column store — logs & history

  • Append-only run events: scheduled, started, heartbeat, completed, failed.
  • Partition key (tenant_id, job_id); cluster key event_time for time-range scans.
  • High write throughput (~12k events/s at peak) without touching Postgres hot rows.
  • Retention policy per tenant; cheap historical queries for debugging and SLA reporting.
Separation rule. Postgres answers "what should run and what state is it in?" Redis answers "what fires in the next 60 seconds?" The broker answers "what is waiting to execute durably?" Cassandra answers "what happened, in order?"

🔗 5. API & database design

The API is the contract between product teams and the dispatch plane. Writes land in Postgres (config) and Redis (timer/buffer); execution handoff goes through the message broker.

API surface
Method Endpoint Purpose Idempotent
POST /v1/jobs Submit job. Writes config to Postgres; seeds Redis timer/buffer. Header: Idempotency-Key. Yes
GET /v1/jobs/{job_id} Job status + latest run attempts. Read from Postgres replica. —
POST /v1/jobs/{job_id}/cancel Cooperative cancel. Revokes Redis lease; marks run cancelled in Postgres. Yes
POST /v1/workers/register Worker advertises capacity tags (region, gpu, slots). Stored in Redis hash + Postgres. Yes
POST /v1/workers/{worker_id}/heartbeat Extend lease TTL in Redis; report slot usage. Internal gRPC from worker to scheduler shard. Yes
POST /v1/runs/{run_id}/complete Terminal state + output ref. Updates Postgres; appends completion event to Cassandra. Yes

Workers consume from the message broker internally — not through the public L7 path.

PostgreSQL tables

Relational — job config & state

  • jobs — immutable intent: job_id, queue_id, schedule_cron, priority, payload_ref, retry_policy. PK: job_id.
  • runs — execution attempts: run_id, job_id, state, attempt, worker_id, worker_host, last_heartbeat_at, scheduled_at, completed_at. Index: (queue_id, state, priority DESC) and (worker_id) WHERE state = 'running'.
  • queues — tenant queue config: concurrency caps, broker topic mapping, retention policy.
Cassandra + broker

Events & execution handoff

  • run_events (Cassandra) — (tenant_id, job_id) partition; columns: event_time, event_type, run_id, detail.
  • execution_queue (Kafka topic) — message: {run_id, job_id, payload_ref, attempt}. Partitioned by queue_id.
  • dlq_topic (Kafka) — poison messages after max retries; mirrored in Postgres dead_letter table for ops UI.

Scheduler handoff — Redis timer fires, broker receives durable intent:

-- Scheduler node: pop due job from Redis timer ZSET
-- 1. ZRANGEBYSCORE timers:{queue_id} -inf {now} LIMIT 0 1
-- 2. Publish to Kafka topic execution.{queue_id}
-- 3. ZREM timer key; UPDATE runs SET state='queued' in Postgres

await producer.send("execution.etl", {
  run_id, job_id, payload_ref, attempt, fire_at

🔄 6. Core end-to-end flow

Three flows matter in production: the happy path, the failure path, and the scale path. Google's Borg paper separates cell scheduling from cluster management; we apply the same split — a stateless-ish scheduler shard per queue partition, and a worker fleet that owns execution.

6.3 Worker placement — which node runs what?

This is the question every on-call engineer asks first. The answer lives in three places — none of them guessed.

Authoritative state

Postgres runs row

  • When a worker consumes a broker message, it immediately writes worker_id, worker_host, state = running, and last_heartbeat_at to Postgres.
  • GET /v1/jobs/{job_id} and GET /v1/runs/{run_id} return the assigned worker — this is what the ops UI shows.
  • Index (worker_id) WHERE state = 'running' answers "what is this node doing right now?" in one query.
Fast lookup

Redis worker registry

  • HSET worker:{worker_id} — host, pool, region, free slots, last_seen.
  • SADD worker:{worker_id}:runs — active run_id set; removed on complete.
  • Sweeper scans workers where last_seen > 30s ago — marks node suspect before Postgres is updated.

What the app guarantees. You always know which worker last claimed a run via Postgres. You detect failure via missed heartbeats (Redis registry + sweeper), not by polling the broker. Redelivery is the broker's job; idempotency is the worker's job. If the target side effect already happened (payment sent), the retry path must read Postgres/Cassandra before re-executing.

⚡ 7. Core design principles

These are the rules we enforce in design review — each borrowed from a production lineage, not a blog checklist.

Four stores, four jobs

Postgres for config, Redis for timers, broker for durable execution, Cassandra for history — never merge write paths.

Trade-off: four systems to operate; each scales independently under real load.

Broker decouples schedule from execute

Scheduler publishes intent; workers consume at their own rate. Redis timers stay small and fast.

Trade-off: at-least-once delivery; workers must be idempotent.

Separate intent from execution

Job metadata (small, transactional) lives in the DB; payloads (large, immutable) live in object storage.

Trade-off: two systems to operate; essential past ~100 KB payloads.

Shard by queue, not by job

Route hash(queue_id) to scheduler shards so hot tenants don't stall cold ones.

Trade-off: cross-queue fairness needs a separate global priority layer (defer v2).

State machine, not flags

Runs transition through enumerated states with allowed edges; no ad-hoc boolean columns.

Trade-off: more ceremony in code; prevents "stuck in limbo" bugs at scale.

Push backpressure to submitters

When queue depth exceeds SLO, return 429 or delay accept — don't buffer unbounded hope.

Trade-off: callers need retry logic; platform survives traffic spikes.

Observable poison

Dead-letter with reason codes (timeout, oom, bad_payload) — operators need triage, not grep.

Trade-off: DLQ hygiene becomes an on-call duty; still cheaper than silent loss.

🩹 8. Pain points

These are not abstract distributed-systems concerns — they are specific failure modes of this app shape: relay + task management up front, Redis timers in the middle, broker handoff, stateless workers at the edge.

Task management becomes a dumping ground

Teams push retry logic, payload validation, and quota checks into task management because it owns the API. Within a quarter it is a god-service. Keep it thin: validate, persist config, seed Redis — push execution policy to scheduler and workers.

Redis timer drift under load

At 10k req/s the scheduler cannot pop every due timer in one tick. Jobs fire late — not failed, just delayed. The app needs a visible scheduled_at vs fired_at skew metric; product teams will treat silent delay as a bug.

Orphaned runs after worker loss

Postgres says running but the worker is gone. Without a sweeper that reconciles Redis heartbeats against runs.worker_id, jobs sit stuck until manual intervention. This is the most common on-call page for new scheduler deployments.

Broker lag looks like a scheduler bug

Users see "queued" in Postgres but nothing executes. Root cause is often consumer lag, not Redis or the scheduler. The app must expose broker depth per queue in the same dashboard as job status — otherwise ops debugs the wrong layer.

Duplicate side effects on redelivery

Worker A charges a card, crashes before complete, Worker B retries. The app layer must check run_id idempotency before calling the target — the scheduler cannot do this for you. Document it in the worker SDK, not a wiki page.

Cassandra history without a query model

Dumping every heartbeat to Cassandra feels safe until someone asks "show me all failed runs for tenant X last Tuesday." Define query patterns upfront — partition by (tenant_id, job_id), not by event type alone.

Multi-tenant fairness in one broker topic

A single execution.default topic lets one tenant's backfill starve another's alerts. The app needs per-tenant concurrency caps enforced at consume time, not just at submit time.

🎯 9. Conclusion

A distributed scheduler at 10k req/s is a four-store pipeline: PostgreSQL holds job config, Redis drives high-precision timers and the near-term buffer, a message broker carries durable execution intent, and Cassandra absorbs run history. Relay and task-management services handle submit; scheduler and worker nodes scale independently on the execute path.

Build this when you need tenant-specific queues, custom capacity tags, or cost control that managed offerings (Cloud Scheduler, Step Functions) cannot match. Buy Temporal or a managed workflow engine when you need durable sagas, human-in-the-loop, and versioned workflow code — that is a superset problem with a higher operational price tag.

If you remember one line: Postgres remembers the plan, Redis times the plan, the broker delivers the plan, Cassandra records what happened.
