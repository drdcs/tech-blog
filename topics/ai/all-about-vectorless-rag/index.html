All About Vectorless RAG

Do we really need a vector database for Retrieval-Augmented Generation? A field guide to lexical search, hierarchical document trees, agentic navigation, the real cost picture, and how to pick the retriever that matches the shape of your information.

For the last few years, building a Retrieval-Augmented Generation application has usually meant following the same architecture:

Documents → chunks → embeddings → vector database → similarity search → LLM

That pattern works extremely well, and dense retrieval was part of the original influential RAG work: the 2020 RAG paper used a dense vector index as non-parametric memory for retrieval. But an interesting question is becoming increasingly important: does every RAG system actually need embeddings and a vector database?

The answer is no. A growing class of systems — often called Vectorless RAG — retrieves information using full-text search, document structure, metadata, SQL, hierarchical indexes, regular expressions, search tools, or LLM-guided navigation instead of dense-vector similarity.

Recent research makes this more than an architectural thought experiment. An AWS study found that an agent equipped only with keyword-oriented document-search tools could achieve more than 90% of the measured performance of its traditional vector-RAG baseline without maintaining a standing vector database. Projects such as PageIndex take a different vectorless approach: convert long documents into hierarchical, table-of-contents-like trees and let an LLM agent reason through that structure to locate relevant pages.

Vectorless RAG therefore deserves serious consideration — but it is not automatically better than vector RAG. The interesting question is not “Should we stop using vectors?” It is: “What retrieval mechanism best matches the information we are trying to retrieve?”

🔍 1. What is Vectorless RAG?

Vectorless RAG is Retrieval-Augmented Generation where the retrieval layer does not require dense embeddings and nearest-neighbor vector search. Traditional vector RAG generally chunks a document, embeds every chunk, stores those vectors in a database, embeds the query, and runs a similarity search. A vectorless system instead preserves text and structure, builds a lexical or structural index, and searches, reasons, or navigates to the exact sections it needs.

The retrieval mechanism could be BM25, SQLite FTS, PostgreSQL full-text search, OpenSearch, SQL queries, metadata filters, regex, a hierarchical tree, or an agent repeatedly using several of those tools. For example, OpenSearch uses BM25 as its default text-relevance algorithm, while PostgreSQL provides dedicated tsvector and tsquery types for full-text retrieval, and SQLite ships the FTS5 extension for efficient full-text searching over document collections.

Key insight. Vectorless does not mean indexless. It usually means replacing a dense-vector index with a lexical, structural, relational, or agent-navigable index.

🌗 2. Two important types of Vectorless RAG

There are currently two particularly interesting patterns.

Search-based Vectorless RAG

The first uses conventional information-retrieval technology such as BM25, full-text indexes, SQL, regex, metadata filters, and search commands. The LLM can run a search once, or it can behave like an agent — the same way a human researcher works: form a query, inspect results, refine, then open the relevant section.

The AWS paper Keyword Search Is All You Need implemented an agent that could inspect PDF metadata and repeatedly use tools such as ripgrep-all and pdfgrep. Across its evaluated datasets, the keyword agent maintained competitive performance with vector RAG, with average relative attainment above 88% across all three reported metrics. On the FinanceBench subset used in the experiment, the agent averaged 30.40% answer correctness versus 24.24% for the study's traditional RAG configuration.

Those numbers are not proof that keyword search universally beats vectors. They show something more useful: iterative search plus LLM reasoning can compensate for the absence of embedding retrieval in some document-QA workloads.

Tree-based / reasoning-based Vectorless RAG

The second approach preserves document hierarchy. PageIndex is a prominent open-source example. Instead of splitting a 300-page report into arbitrary 500-token chunks, it generates a hierarchical tree containing section names, page ranges, summaries, and child sections. At query time, an agent looks through that tree and requests only the relevant pages.

Where vector similarity searches for chunks that are linguistically similar to the question, a tree-based agent reasons about which sections a human would open — Cash Flow, Revenue, and the Working Capital note — then retrieves and compares them. PageIndex describes this as a two-stage process: generate a table-of-contents-like tree, then perform reasoning-driven retrieval through tree search. The team reports its Mafin 2.5 system achieved 98.7% accuracy on the full FinanceBench dataset — a project-reported result rather than evidence that all tree-based systems will match it, but a striking demonstration on highly structured financial documents.

💡 3. Why is Vectorless RAG important?

The biggest issue with embedding retrieval is that semantic similarity is not always the same thing as task relevance. Imagine a technical manual containing an entry like Error E105: Motor temperature exceeded 95°C. If a user asks “What causes E105?”, an exact lexical search for E105 is almost perfect. There is little benefit in computing semantic similarity across hundreds of thousands of embeddings.

The same is true for many enterprise identifiers:

  • SKU-48291, INC-293842, RFC-1053, ErrorCode=PX104
  • API method names, table names, part numbers
  • Policy IDs and contract clause numbers

Dense vectors shine when…

  • Users express the same idea in completely different language
  • Paraphrase and synonym matching matters
  • The corpus is loosely structured

Keyword / structure shines when…

  • The exact symbol, number, or entity matters
  • A heading, relationship, or location matters
  • Precision beats fuzzy recall

That distinction is fundamental — and it is exactly what a single embedding index tends to blur.

✅ 4. Where Vectorless RAG works especially well

Vectorless RAG becomes particularly attractive for long, structured documents: financial reports, legal contracts, regulations, policies, technical manuals, academic material, specifications, runbooks, and operational documentation. PageIndex specifically targets these professional documents because their section hierarchy carries retrieval information that ordinary fixed-size chunking can discard.

It is also compelling for code search, logs, incident reports, support tickets, exact product identifiers, configuration repositories, SQL/database-backed knowledge, frequently changing data, and environments where an organization already operates a mature enterprise-search platform.

Frequently updated knowledge is a standout case. The AWS researchers highlighted it because keyword-oriented agentic search does not require re-maintaining a standing dense-vector database every time knowledge changes.

🧲 5. Where traditional vector RAG is still better

Vectorless RAG is not a universal replacement. Consider a document that says “Employees may work away from their assigned office for a maximum of three days each week,” and a user who asks “What is the remote-working policy?” The document never uses the phrase remote working. Semantic embeddings easily connect remote working with work away from assigned office. A basic keyword search may not.

OpenSearch's own documentation makes the same distinction: BM25 works well for keyword-oriented retrieval but does not capture semantic meaning the way embedding-based approaches do. That makes vector retrieval especially useful for fuzzy discovery, heterogeneous knowledge bases, questions full of synonyms or paraphrases, multilingual semantic retrieval, recommendations, broad exploratory search, and corpora where document structure is weak.

So the production decision is usually more nuanced than vector versus vectorless. Often the strongest architecture fuses several retrievers:

💰 6. Compute and storage cost

This is where the comparison becomes especially interesting. Consider an illustrative knowledge base of 1,000,000 passages, averaging 500 tokens each — 500,000,000 tokens total.

Assume a vector architecture embeds those 500M tokens with text-embedding-3-small, listed at $0.02 per million input tokens: 

500M / 1M × $0.02  =  $10

That is surprisingly small — which reveals an important point: embedding API cost itself may not be the major cost of modern vector RAG. Storage, index memory, replication, infrastructure, re-indexing, operations, retrieval compute, reranking, and generation may matter much more.

Suppose those one million passages use a 1,536-dimensional float32 embedding:

1,000,000 × 1,536 dims × 4 bytes  =  6.144 GB

That is roughly 6.1 GB of raw vector values alone, before ANN index structures, document text, metadata, replicas, backups, or database overhead. At 3,072 dimensions it doubles: 

1,000,000 × 3,072 × 4  =  12.288 GB

OpenAI notes that larger embedding representations consume more compute, memory, and storage; its large embedding model supports up to 3,072 dimensions. Query-embedding cost, by contrast, is almost irrelevant — one million 20-token queries costs 20M × $0.02 / 1M = $0.40.

But Vectorless RAG is not automatically cheaper

A simple BM25 or PostgreSQL full-text system can be extremely economical because no LLM is needed for retrieval. But agentic Vectorless RAG can move compute cost from ingestion to query time. Assume a vectorless agent performs one retrieval-planning LLM call per query with 400 input and 80 output tokens, using GPT-5 mini ($0.25/M input, $2.00/M output): 

Input:   400 / 1M × $0.25  = $0.00010
Output:   80 / 1M × $2.00  = $0.00016
Plan:                      ≈ $0.00026 / query

1,000,000 queries          ≈ $260

And an agent that performs several reasoning/search iterations could cost more. The full picture:

Cost component Vector RAG Lexical Vectorless Agentic / Tree Vectorless

Dense-vector storageRequiredNoneNone
Full-text / tree indexOptionalRequiredUsually required

Takeaway. Vectorless RAG can reduce infrastructure and indexing complexity, but reasoning-based Vectorless RAG can increase per-query compute and latency. The AWS study similarly notes that tool-augmented approaches reduce vector-database maintenance but may introduce latency and operational dependencies of their own.

⚡ 7. Efficiency: which one is faster?

There is no universal winner. A dense ANN lookup is extremely suitable for high-volume, single-shot retrieval. A BM25 / full-text lookup is also highly optimized and can be extremely efficient. But an agent that searches, inspects, searches again, opens a document, inspects a section, and then answers has inherently more sequential work.

Its strength is not necessarily raw latency — it is better retrieval decisions for questions that require navigation and reasoning. This creates a core engineering trade-off:

Traditional vector RAG

  • More indexing / storage infrastructure
  • Cheap retrieval-time computation
  • Great for high-QPS single-shot lookups

Agentic vectorless RAG

  • Less vector infrastructure
  • Potentially more retrieval-time reasoning
  • Great for navigation-heavy questions

Tree-based approaches partly compensate by keeping retrieved context focused. PageIndex deliberately lets an agent inspect the document structure and request specific page ranges rather than loading the complete document.

🗄️ 8. Where should the documents be stored?

Vectorless RAG does not mean putting every source document directly inside an LLM. A good architecture separates the source of truth from the retrieval index — the original document remains authoritative, and the index or tree stays rebuildable.

🛠️ 9. A minimal Vectorless RAG implementation

We can build a surprisingly useful prototype with just Python + SQLite FTS5 + the OpenAI API — no embedding model, no vector database, and no cosine similarity. Create a documents directory of .txt/.md files, install the client with pip install openai, and run the pipeline below. 

import os
import re
import sqlite3
from pathlib import Path

from openai import OpenAI

DB_PATH = "knowledge.db"
DOCS_PATH = Path("./documents")

client = OpenAI()

# 1. Create a full-text search index
def create_index():
    db = sqlite3.connect(DB_PATH)
    db.execute("""
        CREATE VIRTUAL TABLE IF NOT EXISTS docs
        USING fts5(
            path UNINDEXED,
            section,
            content,
            tokenize='porter'
        )
    """)
    db.commit()
    return db

# 2. Split documents by Markdown headings
def split_document(text):
    sections = []
    current_title = "Document"
    current_text = []
    for line in text.splitlines():
        if line.startswith("#"):
            if current_text:
                sections.append((current_title, "\n".join(current_text)))
            current_title = line.lstrip("#").strip()
            current_text = []
        else:
            current_text.append(line)
    if current_text:
        sections.append((current_title, "\n".join(current_text)))
    return sections

# 3. Index documents
def ingest(db):
    db.execute("DELETE FROM docs")
    for path in DOCS_PATH.glob("*"):
        if path.suffix.lower() not in {".txt", ".md"}:
            continue
        text = path.read_text(encoding="utf-8", errors="ignore")
        for section, content in split_document(text):
            db.execute(
                "INSERT INTO docs(path, section, content) VALUES (?, ?, ?)",
                (str(path), section, content),
            )
    db.commit()

# 4. Convert a user question into an FTS query
def build_search_query(question):
    words = re.findall(r"[A-Za-z0-9_]+", question.lower())
    words = [word for word in words if len(word) > 2]
    return " OR ".join(words[:15])  # OR improves recall

# 5. Retrieve relevant sections
def search(db, question, limit=6):
    query = build_search_query(question)
    rows = db.execute(
        """
        SELECT path, section, content, bm25(docs) AS score
        FROM docs
        WHERE docs MATCH ?
        ORDER BY score
        LIMIT ?
        """,
        (query, limit),
    ).fetchall()
    return rows

# 6. Ask the LLM using retrieved evidence
def answer_question(db, question):
    results = search(db, question)
    if not results:
        return "No relevant evidence was found."

    context_parts = []
    for path, section, content, score in results:
        context_parts.append(f"SOURCE: {path}\nSECTION: {section}\n\n{content}")
    context = "\n\n---\n\n".join(context_parts)

    prompt = f"""
Answer the question using ONLY the supplied evidence.
If the evidence is insufficient, say so.
Cite the source file and section used in the answer.

QUESTION:
{question}

EVIDENCE:
{context}
"""
    response = client.responses.create(model="gpt-5-mini", input=prompt)
    return response.output_text

if __name__ == "__main__":
    db = create_index()
    ingest(db)
    question = input("Question: ")
    print(answer_question(db, question))

The pipeline is now Documents → SQLite FTS index → BM25-style lexical retrieval → top sections → LLM. No embeddings are generated.

🤖 10. Making the example more powerful

The simple implementation struggles with synonyms. Ask “Can employees work remotely?” when the document says “Associates may perform duties away from their assigned office three days per week,” and a lexical search may miss it. The next step is agentic query rewriting: before searching, ask a small model to expand the query into terms like remote work, work from home, away from office, offsite work. Search all of them, inspect the results, and search again if the evidence is weak.

🌲 11. PageIndex: a more advanced example

Instead of a lexical index, PageIndex converts long documents into hierarchical structures. Its open-source README shows PDF indexing with python3 run_pageindex.py --pdf_path /path/to/document.pdf, plus a faster --flash preview path. Flash mode determines document structure heuristically without an LLM, while an LLM is still used when generating node summaries.

The repository's end-to-end agentic example gives an agent three important tools:

  • get_document()
  • get_document_structure()
  • get_page_content()

The agent first inspects the hierarchy, decides which page range is relevant, retrieves those pages, and then answers — a useful mental model for sophisticated Vectorless RAG.

🎯 13. The most important architectural lesson

The real lesson from Vectorless RAG is not that vector databases are obsolete. It is that we spent several years treating RAG as though it meant chunking + embeddings + vector database. It does not. RAG only requires that we retrieve useful external evidence before generation — and the retriever could be vector search, BM25, SQL, metadata, graph traversal, document hierarchy, an API lookup, regex, filesystem search, web search, or an agent combining several of them.

Retrieval should match the shape of the information. Millions of short, loosely structured documents with fuzzy questions → vectors. Structured 200-page reports, exact identifiers, fast-changing ops docs, code, logs, contracts → Vectorless RAG. Both kinds of question → hybrid retrieval.

Final recommendation

Do not start a RAG project by asking “Which vector database should we use?” Start with representative questions and ask: “What information would a human need to retrieve to answer these, and how would the human find it?”

If a human would…Use
“Find documents discussing the same concept”Vectors
“Find this exact identifier or phrase”Lexical search
“Open the relevant chapter and inspect related sections”Hierarchical / agentic retrieval
“Query these structured facts”SQL
Ask all of the aboveCombine retrieval strategies

That, more than eliminating vector databases, is why Vectorless RAG matters. It moves RAG architecture away from similarity-first retrieval and toward relevance-first retrieval.
