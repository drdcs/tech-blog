Thinking in Flink (and When Spark Is Enough)

A plain-English take on Apache Flink vs Spark Structured Streaming. Not a feature checklist — just the simple mental models I use when a stream is driving live app state, and the real-world headaches each engine brings.

💬 1. Introduction

Before the head-to-head, here's each engine in one sentence:

Spark Structured Streaming. It treats a live stream like a table that keeps growing, and runs your query over and over on small batches of new data.
Apache Flink. It's built for streaming from the ground up — each record flows through the pipeline the moment it shows up, with no waiting for a batch.

Both are great tools. Below I walk through the same ten topics for each one. Since the main reason I reach for Flink is how it behaves in production, I've put the common headaches right in the Flink column instead of hiding them.

If you came here from Consuming Streaming Data in BigQuery at Scale, this is the flip side. That post said you can skip a streaming engine for simple append-only loads. This one is about the jobs where you actually want one.

🖼️ 2. The picture in my head

The setup I keep coming back to is Kafka → Flink → a store that's always up to date (Bigtable, for me). Events come in, Flink groups them by key and by time window, a watermark moves time forward, windows fire, and the results get written to the store as they change. 🔁 3. Processing model

Spark Structured Streaming

  • Think of it as micro-batch: it collects events into small batches and processes them one batch after another.
  • Your delay depends on how often batches run and how long each one takes.

Apache Flink

  • It runs all the time as a live pipeline.
  • Records move through as they arrive — nothing waits for a batch to close.
  • Latency is lower and steadier, but you're always running (and paying for) a live job.

⏱️ 4. Watermarks & event time

Spark Structured Streaming

  • Watermarks are tied to how far each batch/query has gotten.
  • So I usually think about late data at batch edges.
  • Works well for normal “watermark + aggregate” jobs.

Apache Flink

  • Watermarks flow through the whole pipeline and directly drive time-based windows and timers.
  • That gives you much finer control when data arrives out of order.
  • Watch out: if a source goes quiet or is set up wrong, the watermark stops moving and windows never fire — one silent partition can freeze time for everything downstream.

🧠 5. State management

Spark Structured Streaming

  • Operators can keep state across batches.
  • It works well, especially for jobs that do a lot of aggregation.
  • I tend to think about state as part of the query.

Apache Flink

  • State is a core, built-in idea.
  • After keyBy, each task owns part of a distributed memory: keyed state, timers, checkpoints, and a place to store it all (the state backend).
  • Watch out: if state keeps growing forever, it fills up disk/memory. Setting expiry (TTL) and cleanup isn't optional — it's essential.

🚰 6. Backpressure

Spark Structured Streaming

  • My main question: “can each batch finish before the next ones pile up?”
  • Slow batches directly add delay.
  • The batch is the thing I tune around.

Apache Flink

  • Backpressure spreads back through the live pipeline.
  • You can see exactly which step is slow.
  • Really handy when Kafka, Bigtable, or another sink starts slowing down — the slow spot lights up.

💾 7. Checkpointing & recovery

Spark Structured Streaming

  • Checkpoints track how far the query got and its state.
  • If it fails, it restarts and keeps going.

Apache Flink

  • A checkpoint is a consistent snapshot of where you are in the source + all operator state + timers.
  • After a crash, Flink loads that snapshot and replays the records that came after it.
  • Watch out: lots of state means slow checkpoints that can time out — a stuck checkpoint causes restarts and lost throughput at the worst moment.

🔂 8. Replay & exactly-once

Spark Structured Streaming

  • Its batch model makes exactly-once fairly easy for supported sinks.
  • External sinks still need to be set up correctly.

Apache Flink

  • After recovery, Flink may replay Kafka events.
  • So I make the Bigtable writes idempotent — the same input always writes to the same row (stable row keys / timestamps).
  • The truth: “exactly-once into an outside store” is really “at-least-once + safe repeated writes.” Get the row key wrong and replays double-count.

🐢 9. Late events

Spark Structured Streaming

  • Fine for normal watermark + aggregation jobs.
  • You handle late data at the query level.

Apache Flink

  • This is where Flink really shines for me.
  • Watermarks, event-time timers, allowed lateness, late firings, and side outputs give you fine control.
  • Late data doesn't have to be thrown away — you can send it aside, re-run a window, or reconcile it later.

🔥 10. Hot keys & skew

Spark Structured Streaming

  • A skewed key can blow up state or slow down tasks/batches.
  • How you partition still matters a lot.

Apache Flink

  • A hot keyBy value can overload one specific task.
  • That causes backpressure, slower checkpoints, and an obvious bottleneck in production.
  • Watch out: one “celebrity” key (a huge customer, a viral device) can drag the whole job. Common fixes are pre-aggregating or “salting” the key to spread it out.

🛠️ 11. Operational difficulty

Spark Structured Streaming

  • Often easier if your team already runs Spark for ETL, SQL, and ML.
  • One platform can do both batch and streaming.
  • Fewer streaming-only settings to learn.

Apache Flink

  • More streaming-specific tuning: parallelism, checkpoints, state storage, idle watermarks, backpressure, restart settings, savepoints, and state growth.
  • You get more control, but there's more to operate.
Side-by-side mental model. Spark: streaming that works like batch/dataframe code run over and over. Flink: a live, always-on engine that reacts to each event and remembers state as it goes.

🧭 12. When I'd use each

I'd reach for Spark when…

  • Your work is mostly SQL, ETL, aggregations, and data engineering, and streaming is just one part of a bigger Spark setup.
  • A few seconds of delay is fine — you don't need sub-second.
  • Your team already knows Spark and wants batch + streaming on one platform.
  • You want an easy path from an existing Spark batch job into streaming.

I'd reach for Flink when…

  • The app is truly streaming-first — always on, not periodic batches.
  • You have tricky time logic: watermarks, timers, out-of-order data, sessions, late events.
  • You keep a lot of long-lived state per key — customer_id, device_id, order_id, session_id.
  • You need tight control over latency, backpressure, checkpoints, replay, and recovery.
  • The pipeline looks like Kafka → your logic → an always-updated Bigtable/online store.
My quick rule. If it's mostly analytics/ETL that happens to read Kafka, I lean Spark. If Kafka events are driving live app state in Bigtable — with watermarks, late data, replay, and low latency — I lean Flink.
