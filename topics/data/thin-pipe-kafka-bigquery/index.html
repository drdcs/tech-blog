The Thin Pipe

Kafka to BigQuery on the Storage Write API — a memory-efficient, gRPC-native data flow you can scale on Kubernetes without paying the Spark or Flink cluster tax.

1. The thesis

Most Kafka → warehouse pipelines are overbuilt. Teams reach for Spark Structured Streaming or Flink because those tools are excellent at stateful stream processing — windows, joins, exactly-once across complex DAGs. But a large class of workloads is simpler: consume, validate, map to a typed row, append to BigQuery.

For that shape, a thin consumer plus the BigQuery Storage Write API wins on memory, cost, and operational surface. You keep hot state in Kafka offsets (and maybe a tiny in-process buffer), speak protobuf over gRPC to BigQuery, and scale with Kubernetes HPA — one pod per partition group, not one JVM cluster per pipeline.

2. A short history of the BigQuery Storage Write API

BigQuery’s write story evolved in three eras:

  1. Load jobs (batch). Upload Avro/Parquet/CSV to GCS, run a load job. Cheap and durable, but minutes of lag — fine for warehouses, painful for near-real-time product analytics.
  2. Streaming inserts (tabledata.insertAll). REST JSON rows into a streaming buffer. Easy to adopt, but higher per-row cost, weaker throughput ceilings, and awkward semantics around duplicates and when data lands in durable storage / partitions.
  3. Storage API era (~2021–2022+). Google opened a high-throughput binary path. The Storage Read API landed first for arrow/avro consumers; the Storage Write API followed as the modern write surface — gRPC streams, protobuf (or Arrow) payloads, committed / pending stream modes, and a design aimed at exactly-once style ingestion without JSON tax.

Today, for sustained Kafka drains, Storage Write is the default recommendation when you care about cost per GB, memory on the producer side, and predictable commit semantics. The thin pipe in this essay sits squarely in that third era.

3. Thin-pipe architecture

The pipeline is deliberately boring. Kafka holds the durable log. Workers are stateless besides consumer offsets and a small append buffer. BigQuery is the analytical destination. No shuffle, no RocksDB state backend, no checkpoint coordination service.

4. gRPC & protobuf on the wire

Storage Write speaks gRPC. Workers open a bidirectional stream and call AppendRows with serialized payloads. Compared with REST JSON inserts you avoid: text encoding bloat, repeated schema keys per row, and HTTP/1 chatty connection behavior. Protobuf (or Arrow) keeps CPU on both sides predictable.

Practically you maintain a .proto that mirrors the BigQuery table schema (or a stable subset). Codegen produces language bindings; the worker maps Kafka messages → proto messages → append requests. Schema evolution is intentional: add optional fields, version the proto, and roll workers behind a compatible BigQuery schema update.

5. Destination loader (BigQuery)

Think of the worker’s BigQuery side as a destination loader: a small module that owns stream lifecycle, retries, and backpressure — not business logic. Responsibilities:

  • Create or attach to a write stream (default, committed, pending, or buffered — see next section)
  • Batch proto rows into AppendRows frames sized for throughput (often hundreds of KB to a few MB)
  • Handle flow control / RESOURCE_EXHAUSTED with exponential backoff
  • Only then acknowledge Kafka offsets — so BigQuery durability leads consumer progress
  • Emit metrics: append latency, rows/s, bytes/s, error class, stream recreates

6. Write stream types & how upserts work

The Storage Write API is stream-oriented. Before you call AppendRows, you choose (or inherit) a write stream type. That choice controls when rows become queryable and how you get exactly-once / atomic visibility.

Stream types

Type Visibility When to use
Default stream Queryable as soon as append is ACK’d Simplest thin pipe; at-least-once if you retry after ACK loss
Committed stream Visible immediately after successful append You manage stream create/lifecycle; low-latency reads
Pending stream Hidden until Finalize + BatchCommit Atomic “all rows appear together”; multi-stream commit
Buffered stream Visible up to a flushed offset Fine-grained commit cursor via FlushRows
  • Default stream (_default) — no stream create call; every successful append is committed. Ideal for continuous Kafka drains where seconds of visibility lag are fine and duplicates are handled downstream (or via CDC upsert keys).
  • Committed stream — CreateWriteStream(type=COMMITTED). Same immediate visibility model as default, but you own the stream name/lifecycle (recreate on failure, pin per worker, etc.).
  • Pending stream — appends land in a non-queryable pending area. You FinalizeWriteStream, then BatchCommitWriteStreams for one or more streams. Readers never see a partial micro-batch — powerful for “exactly once visibility” of a Kafka offset window.
  • Buffered stream — append freely, then FlushRows up to an offset so only the flushed prefix becomes durable/visible. Useful when you want commit frontiers without full pending-batch ceremony.

How upserts work on the Storage Write API

The write API is append-shaped on the wire, but BigQuery can apply change-data-capture (CDC) upserts/deletes when the destination table declares a primary key (typically NOT ENFORCED). Instead of blind inserts, each row carries change metadata that BigQuery applies against the key:

  • _CHANGE_TYPE — UPSERT or DELETE
  • _CHANGE_SEQUENCE_NUMBER — monotonic per-key ordering so late/duplicate Kafka deliveries do not clobber newer state

Practical thin-pipe pattern for mutable entities (users, orders, CDC from OLTP):

  1. Create the table with a primary key on the business id
  2. Write continuously on the default stream (CDC path is built around it)
  3. Map Kafka compacted/CDC topics → proto/JSON rows including _CHANGE_TYPE
  4. Use sequence numbers from the source LSN / Kafka offset / Debezium pos so retries stay idempotent
-- Destination that supports Storage Write CDC upserts
CREATE TABLE analytics.orders_current (
  order_id STRING NOT NULL,
  status STRING,
  amount_cents INT64,
  updated_at TIMESTAMP
)
PRIMARY KEY (order_id) NOT ENFORCED
PARTITION BY DATE(updated_at);
# Pseudocode row payload for an upsert append
row = {
    "order_id": "ord_9f2",
    "status": "paid",
    "amount_cents": 4599,
    "updated_at": "2026-08-09T09:15:00Z",
    "_CHANGE_TYPE": "UPSERT",
    "_CHANGE_SEQUENCE_NUMBER": "170000000012345",  # source LSN / offset
}
Append vs upsert. Immutable events (clicks, impressions) → plain append on default/committed streams. Mutable snapshots (CDC, entity state) → primary key + _CHANGE_TYPE upserts. Don’t MERGE from staging on every micro-batch if the Storage Write CDC path already fits — that MERGE is where teams accidentally reintroduce Spark-sized cost.

7. Scale with Kubernetes

Horizontal scale maps cleanly to Kafka partitions. Run a Deployment (or StatefulSet) of write workers; each consumer instance in the group receives a subset of partitions. Autoscale on lag (Kafka consumer group lag exporter → HPA / KEDA), not on CPU alone — ingestion is often network and gRPC bound.

  • Partition affinity: more partitions than peak pods; avoid idle executors
  • Requests/limits: start ~256–512Mi request, 1Gi limit per worker for typical row widths
  • PodDisruptionBudgets: keep lag from spiking during node drains
  • Secrets: Workload Identity to BigQuery — no JSON key files on disk

8. Why Spark / Flink is not cost-efficient here

Spark and Flink shine when you need distributed state: session windows, stream–stream joins, CEP, large keyed aggregations. For append-only Kafka → BigQuery, you still pay for:

  • Always-on cluster tax — drivers, task managers, coordinators, checkpoint storage
  • Memory amplification — JVM heap, managed memory, network buffers far above row batch size
  • Operational gravity — savepoints, connector versioning, shuffle / restart semantics for a pipeline that does not need them
  • Cold start & bin-packing waste — executors sized for peaks sit idle at troughs; K8s pods scale to zero/near-zero more naturally with KEDA

If your “processing” is a map and a filter, a ~400MB Python worker writing protobuf over gRPC will usually beat a multi-GB Flink TM on cost per sustained MB/s. Keep Flink/Spark for the jobs that actually need the stateful engine — don’t make them your default warehouse faucet.

Thin pipe on K8s

  • Memory ≈ batch × inflight
  • Scale = partition count
  • State = Kafka offsets
  • Ops = Deployment + HPA

Spark / Flink faucet

  • Memory ≈ executor × parallelism
  • Scale = cluster reshape
  • State = checkpoints + KE
  • Ops = platform team tax

9. Code sketch (Python)

Illustrative hot path using confluent-kafka and the BigQuery Storage Write client patterns. Production code should add metrics, poison handling, and stream recreation on failed appends. 

import json

from confluent_kafka import Consumer
from google.cloud import bigquery_storage_v1
from google.cloud.bigquery_storage_v1 import types, writer

# checkout_event_pb2 is generated from checkout_event.proto
import checkout_event_pb2


PROJECT = "my-project"
DATASET = "analytics"
TABLE = "checkout_events"


def make_consumer() -> Consumer:
    return Consumer(
        {
            "bootstrap.servers": "kafka:9092",
            "group.id": "bq-thin-pipe",
            "enable.auto.commit": False,
            "auto.offset.reset": "earliest",
        }
    )


def to_proto(raw: bytes) -> checkout_event_pb2.CheckoutEvent:
    data = json.loads(raw)
    ev = checkout_event_pb2.CheckoutEvent(
        event_id=data["event_id"],
        event_time_ms=int(data["event_time_ms"]),
        user_id=data["user_id"],
        sku=data["sku"],
        amount_cents=int(data["amount_cents"]),
        currency=data.get("currency", "USD"),
        region=data.get("region", "unknown"),
    )
    return ev


class BQLoader:
    """Destination loader: owns write-stream lifecycle + AppendRows."""

    def __init__(self):
        self._client = bigquery_storage_v1.BigQueryWriteClient()
        self._parent = self._client.table_path(PROJECT, DATASET, TABLE)
        # Default stream: simplest continuous drain (at-least-once).
        self._stream = f"{self._parent}/streams/_default"
        self._append = None

    def open(self):
        request_template = types.AppendRowsRequest()
        request_template.write_stream = self._stream

        proto_data = types.AppendRowsRequest.ProtoData()
        # Attach proto schema / descriptor for CheckoutEvent in real code:
        # proto_data.writer_schema.protobuf.proto_descriptor.CopyFrom(...)
        request_template.proto_rows = proto_data

        self._append = writer.AppendRowsStream(self._client, request_template)

    def append(self, rows: list[checkout_event_pb2.CheckoutEvent]) -> None:
        proto_rows = types.ProtoRows()
        for row in rows:
            proto_rows.serialized_rows.append(row.SerializeToString())

        req = types.AppendRowsRequest()
        req.proto_rows.rows.CopyFrom(proto_rows)
        future = self._append.send(req)
        future.result()  # raise on append error; do NOT commit Kafka yet


def run() -> None:
    consumer = make_consumer()
    consumer.subscribe(["checkout.events"])
    loader = BQLoader()
    loader.open()

    try:
        while True:
            messages = consumer.consume(num_messages=500, timeout=0.5)
            if not messages:
                continue

            rows = []
            for msg in messages:
                if msg.error():
                    raise RuntimeError(msg.error())
                rows.append(to_proto(msg.value()))

            # BigQuery durability first — then Kafka offsets.
            loader.append(rows)
            consumer.commit(asynchronous=False)
    finally:
        consumer.close()


if __name__ == "__main__":
    run()

Optional: pending-stream commit for atomic visibility of one Kafka batch:

def append_pending_batch(client, parent, rows):
    stream = client.create_write_stream(
        parent=parent,
        write_stream=types.WriteStream(
            type_=types.WriteStream.Type.PENDING
        ),
    )
    # ... AppendRows to stream.name for `rows` ...
    client.finalize_write_stream(name=stream.name)
    client.batch_commit_write_streams(
        parent=parent,
        write_streams=[stream.name],
    )

11. Partitioning & staleness — how to set it, why it matters

Partitioning the destination

Partition BigQuery tables on event day (from event_time_ms), not only ingestion time, so late Kafka data still lands in the analytical day dashboards expect. Add clustering on high-cardinality filter columns (region, sku) to cut scanned bytes. Enforce require_partition_filter = true so ad-hoc queries cannot accidentally full-scan years of stream history. 

CREATE TABLE analytics.checkout_events (
  event_id STRING,
  event_time TIMESTAMP,
  user_id STRING,
  sku STRING,
  amount_cents INT64,
  currency STRING,
  region STRING
)
PARTITION BY DATE(event_time)
CLUSTER BY region, sku
OPTIONS (require_partition_filter = true);

What “fresh” means on the write path

With Storage Write (default/committed), rows become queryable quickly after append ACK — often seconds, dominated by your flush interval + gRPC RTT, not by a mysterious multi-minute streaming buffer. Pending streams delay visibility until BatchCommit on purpose. Treat write-side freshness as an SLA you measure (append_ack_latency, kafka_to_bq_visible_p99), not as “eventually sometime.”

How to set staleness in BigQuery

Staleness is configured on materialized views (and respected by queries that can use them) via max_staleness. It tells BigQuery: “It is acceptable to answer from a result that is up to this old.” 

-- Create with an explicit staleness budget
CREATE MATERIALIZED VIEW analytics.checkout_mv
OPTIONS (
  enable_refresh = true,
  refresh_interval_minutes = 10,
  max_staleness = INTERVAL 15 MINUTE
)
AS
SELECT
  DATE(event_time) AS d,
  region,
  COUNT(*) AS events,
  SUM(amount_cents) AS revenue_cents
FROM analytics.checkout_events
WHERE event_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
GROUP BY 1, 2;

-- Or alter later when SLAs change
ALTER MATERIALIZED VIEW analytics.checkout_mv
SET OPTIONS (max_staleness = INTERVAL 5 MINUTE);

-- Dashboard / BI query: allow bounded staleness explicitly
SELECT *
FROM analytics.checkout_mv
FOR SYSTEM_TIME AS OF
  TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 0 SECOND);
-- Prefer querying the MV directly; BigQuery may use last refresh
-- + incremental base-table delta within max_staleness.

Practical guidance for choosing the interval:

  • Ops / fraud / paging — query the base table; do not lean on a 15‑minute MV
  • Product dashboards — INTERVAL 5 MINUTE to 15 MINUTE is a common sweet spot
  • Executive rollups — INTERVAL 30 MINUTE to 1 HOUR is often enough and much cheaper under load

Why staleness is important

Under a thin pipe at high ingest, the base table is always moving. If every Looker/Metabase tile hits the live fact table with tight freshness, you pay:

  • Slot contention exactly when Kafka lag (and business attention) peaks
  • Unstable dashboard latency — query plans fight a hot streaming tail
  • Redundant aggregation of the same seconds-old data across hundreds of concurrent readers

max_staleness decouples write freshness from read freshness. Writers keep committing as fast as Storage Write allows; readers declare a budget so BigQuery can reuse refreshed MV state and only apply a bounded delta. That is how you keep the pipe thin and the warehouse calm.

High-scale events: time to resolve after staleness is set

“Time to resolve” here means: how long until a high-scale burst of events shows up as a stable number in the table/MV your consumers trust. With staleness configured, that clock has two layers:

Layer Typical resolve time What it means
Base table (default/committed) ~1–5 s p50, ~5–30 s p99 Event is queryable after append ACK + flush
MV inside max_staleness ≤ staleness interval Dashboard may legally lag up to the budget
MV after a traffic spike often still ≤ max_staleness BQ serves last good refresh + delta instead of full re-agg
Pending-stream batch hidden until BatchCommit Resolve time = your commit cadence (e.g. every 2–10 s)

Example: you set max_staleness = INTERVAL 15 MINUTE and a flash sale suddenly pushes 10× events. The thin pipe still lands rows into the base table in seconds. BI tiles querying the MV do not each re-scan the entire hot partition on every refresh — they resolve within the 15‑minute staleness envelope, so query latency stays flat while ingest spikes. If a stakeholder needs “right now” revenue during the sale, point them at a base-table monitor with a partition filter — not at every executive dashboard.

Design split. Optimize the write path for memory-efficient freshness (stream type + flush). Optimize the read path with partition filters and an explicit max_staleness budget. At high scale, staleness is not “bad data” — it is how you keep time-to-resolve predictable.

Closing

The thin pipe is a bet on the right tool for Kafka drains: protobuf over gRPC, the right Storage Write stream type (default / committed / pending / buffered), CDC upserts when entities mutate, Kubernetes for elastic scale, and partitioned tables plus max_staleness so analytics can be deliberately, productively stale.

Keep Spark and Flink for stateful stream brains. For the faucet into BigQuery, ship a thin pipe.
